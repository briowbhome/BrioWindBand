# 音樂會管理與分部指派 — 設計文件

**日期**：2026-08-24
**狀態**：設計已與使用者確認，待寫實作計畫
**範圍**：這份文件只涵蓋「操作介面」層面的設計（資料模型 + UI 流程）。**權限細節**（`firestore.rules` 怎麼限制分部長只能寫自己負責的樂器分部、`concert-admin` 相關功能的存取層級）刻意留到下一輪另外討論，不在這份文件內定案。

## 背景

現有的活動管理（`event-admin.html`）只處理「單日活動」（`events` collection，`date`/`allDay`/`endTime` 綁死單一天）。使用者想擴充出「音樂會」的概念——一個沒有明確時間點、但持續一段期間的專案，底下可能包含多場單日的團練/演出活動，並且需要曲目管理、分部長指派分部、參與者的樂器身分（與個人資料樂器能力不同）等一整套新功能。

## 目標（這輪範圍）

1. 建立「音樂會」實體，可設定期間、說明
2. 音樂會底下可新增/管理曲目
3. 分部長能對自己管轄的樂器分部，針對每首曲子把参與名單中的人指派到自訂的分部欄位（例如 1st/2nd/3rd，欄位由分部長臨時自訂，不是預先定義的固定清單）
4. 管理員能用同一套指派介面，協助調整任何樂器分部（不限自己管轄範圍）
5. 音樂會有自己的參與名單，每個參與者有「這場音樂會負責的樂器」身分（跟個人資料的樂器能力清單分開），這輪只做管理員手動勾選/調整，不做團員自助報名表單
6. 團員可以查看自己在各音樂會被分派到的分部（唯讀）

## 明確排除範圍（這輪不做）

- 權限細則：分部長寫入範圍的 Firestore 規則、`concert-admin` 相關功能的存取層級判斷——下一輪另外討論
- 團員自助勾選「這場音樂會我要負責哪個樂器」的報名表單——資料模型已預留欄位，之後接上時不需要改資料結構
- 分部筆記（團員/分部長對音樂會的筆記功能）——這輪對話中臨時提到的構想，未展開設計，留待之後
- 未來報名表單接上後，參與名單的「樂器」欄位會改成讀報名者自選值而非預設帶入個人資料第一筆樂器——目前只是先記錄這個已知的後續調整方向，不影響這輪資料模型

## 資料模型

### `concerts/{concertId}` — 音樂會主文件

| 欄位 | 型別 | 說明 |
|---|---|---|
| `title` | string | 音樂會名稱，例如「2026 校友團公演」 |
| `startDate` / `endDate` | timestamp | 期間，僅供顯示/排序用，不像 `events.date` 需要精確到時分 |
| `description` | string | 選填說明 |
| `createdBy` | uid | 建立者 |
| `createdAt` | timestamp | 建立時間 |

### `concerts/{concertId}/pieces/{pieceId}` — 曲目子集合

| 欄位 | 型別 | 說明 |
|---|---|---|
| `title` | string | 曲名 |
| `composer` | string \| null | 選填，作曲/編曲者 |
| `order` | number | 顯示排序，比照 `eventTypes.order` 同樣用途 |
| `createdBy` / `createdAt` | uid / timestamp | |

### `concerts/{concertId}/pieces/{pieceId}/sections/{instrumentName}` — 每曲 × 每樂器分部指派

文件 ID 直接用樂器名稱（對應 `settings/instruments` 的 `name`），每首曲子每個樂器分部各自一份文件——**這是刻意的拆分粒度**：如果整首曲子的所有樂器分部指派塞在同一份文件裡，不同分部長（例如單簧管分部長跟長笛分部長）同時編輯同一首曲子時，後寫入的會整份覆蓋前面的結果。拆成「曲目 × 樂器分部」各自一份文件後，不同分部長的寫入天生不會互相衝突。

| 欄位 | 型別 | 說明 |
|---|---|---|
| `parts` | `array<{partId, label, members: array<uid>}>` | 分部欄位清單，由分部長/管理員在指派畫面**臨時自訂**（不是預先定義的固定清單）。如果這首曲子這個樂器不需要細分，就只有一個欄位裝全部人；需要細分時可以自訂命名（例如「1st」「2nd」「3rd」，或其他任意命名） |
| `updatedBy` | uid | 最後編輯者 |
| `updatedAt` | timestamp | 最後編輯時間 |

只有在分部長（或管理員）第一次對某首曲子的某個樂器分部進行指派操作時，才會建立這份文件——沒有指派過的樂器分部不需要預先建立空文件。

### `concertRosters/{concertId}` — 音樂會參與名單

文件 ID 直接用 `concertId`，比照 `eventRosters` 一場活動最多一份的慣例。

| 欄位 | 型別 | 說明 |
|---|---|---|
| `members` | `array<{uid, instrument, name, account}>` | 參與者 + 各自這場音樂會負責的樂器身分。`instrument` 是單一字串（對應 `settings/instruments` 的 `name`），不是陣列——跟 `users.instruments`（個人資料的能力清單，可複選）是不同概念：這裡代表「這場音樂會的參與身分」，只能是一個。`name`/`account` 是寫入當下從 `users` 反正規化複製過來的顯示用欄位：`firestore.rules` 只開放 `isAdminTier()` 對 `users` 做 `list`，分部長（一般團員身分）不能自己撈全團名單來對照人名，只能靠這裡存下來的值顯示。這兩個欄位是快照，不會跟著 `users` 的改名同步，下次名單存檔時才刷新 |
| `sourceTemplateId` / `templateAppliedAt` | string \| null / timestamp \| null | 套用名單範本的來源記錄，比照 `eventRosters` 同樣欄位的語意 |
| `createdBy` / `updatedAt` | uid / timestamp | |

**套用名單範本的行為**：套用範本只帶入範本裡的 uid 清單（範本本身沒有樂器欄位），套用後每個人的 `instrument` **預設帶入 `users.instruments[0]`**，管理員可在參與名單畫面個別調整例外。重新套用範本時的差異提示（新增/移除人數）比照 `eventRosters` 現有的 `confirm()` 模式。

**分部長指派時的可選成員範圍**：分部長在指派畫面只能從「參與名單中 `instrument` 符合自己 `sectionLeaderFor` 的人」裡挑選——參與名單是分部指派的唯一資料來源，不會讓分部長指派到沒有在參與名單中的人。

## 操作介面

### 1. `event-admin.html` 新增「音樂會」區塊

現有頁面已有「活動」列表 + 建立流程，這次在同一個頁面內新增「音樂會」區塊，用切換（比照現有分頁切換的視覺語言）在「活動」/「音樂會」兩個區塊間切換，各自獨立的列表、＋新增按鈕、明細 sheet：

- **音樂會列表**：卡片顯示標題 + 期間，比照活動列表的卡片樣式
- **＋ 新增音樂會**：彈出 sheet 填標題/期間/說明，存檔後不關閉、可連續建立（比照活動建立流程）
- **音樂會明細 sheet**，分頁式：
  - **音樂會資訊**：標題/期間/說明，先看後編模式（比照活動資訊分頁）
  - **曲目管理**：曲目清單（可新增/編輯/刪除/調整排序），點進單一曲目顯示底下所有樂器分部的指派畫面——管理員在這裡可以直接編輯任何樂器分部的指派（不限管理員自己的 `sectionLeaderFor`，因為管理員本來就該有全權調整的能力），跟分部長專屬頁面共用同一套指派互動元件（見下方「共用指派元件」）
  - **參與名單**：比照「名單調整」分頁——勾選團員（或套用名單範本）+ 手動調整每人這場音樂會的樂器身分

**`events` 建立/編輯表單新增選填欄位**：`concertId` 下拉選單（列出既有音樂會，預設「不屬於任何音樂會」），選了之後這場單日活動就會「掛」在該音樂會底下。這個欄位純粹是關聯，不影響 `events.repertoire`（維持獨立的自由文字曲目備註，兩邊不互相同步）。

### 2. 分部長專屬頁面（新頁面，暫定 `section-admin.html`）

比照 `conductor-admin.html` 的既有先例——分部長不一定是 `admin`/`owner` 角色，可能只是一般團員掛 `permissions.sectionLeaderFor`，不能直接開放進 `event-admin.html`（admin-tier 頁面），因此另開一個輕量頁面，動線：

1. 選擇音樂會（列出音樂會清單）
2. 選擇曲目
3. 顯示自己 `sectionLeaderFor` 範圍內樂器分部的指派畫面（見下方「共用指派元件」），**看不到、也不能操作其他樂器分部**

### 共用指派元件（分部長頁面 + 管理員曲目管理分頁共用）

給定「曲目 + 樂器名稱」，畫面呈現：
- 該樂器分部目前的欄位清單（預設一個欄位裝全部人，或已自訂過的多個欄位）
- 「新增分部欄位」按鈕，可自訂命名新欄位
- 從「參與名單中這個樂器的所有人」裡勾選/搬動到不同欄位——具體互動細節（拖曳 vs 勾選＋下拉選欄位）留到寫實作計畫時再定，這裡先定案「共用同一套元件、差別只在可操作的樂器範圍」這個原則

### 3. `index.html`「團務總覽」分頁新增「我的音樂會」區塊

- 列出自己在 `concertRosters` 中出現的音樂會
- 每場音樂會底下列出各曲目，顯示自己被分派到哪個分部欄位（尚未指派時顯示「尚未指派」）
- 唯讀，不可在這裡操作

放在「團務總覽」而非「個人中心」（`profile.html`）的理由：團務總覽本來就是為「跟團務有關但非每日待辦」的資訊預留的分頁（schema 已記錄之後要放團費/行事曆），音樂會內容性質上屬於這一類；`profile.html` 目前只放帳號層級設定（個人資料/密碼/通知開關），放進音樂會內容會偏題。

## 與現有功能的關係

- `events.repertoire`（單日活動自由文字曲目清單）**維持完全獨立**，不讀取、不同步音樂會的結構化曲目資料。兩者是不同層級的資訊：`events.repertoire` 是「這場團練當天要練什麼」的備註，音樂會曲目是「整個專案的完整曲目編制」
- `events` 新增選填 `concertId` 欄位建立關聯，這是唯一的連接點
- 參與名單套用範本機制沿用 `rosterTemplates`/`eventRosters` 既有的套用模式（複製快照、可重新套用整份覆蓋、`confirm()` 顯示差異）
- 分部長 `sectionLeaderFor` 欄位（`roles-admin.html` 已可設定、目前無功能讀取）第一次真正被使用
